# BHub v1.1 — Production Reliability (Plano de Implementação)

Plano consolidado a partir do pacote `bhub_next_development_markdown.zip` (7 arquivos).
Commit de referência: `1d3177e` (verificado — worktree parte dele).

## Milestone

**BHub v1.1 — Production Reliability**

### Definition of Done

- [ ] Nenhuma tarefa crítica de produção depende de `asyncio.create_task()`.
- [ ] O worker de PDF não depende da camada legada `background_tasks.py`.
- [ ] Falha do Redis/ARQ em produção é explícita e observável.
- [ ] Serviços de I/O relevantes podem ser substituídos em testes.
- [ ] `ruff` bloqueia o CI.
- [ ] `mypy` roda no CI.
- [ ] Existe baseline mínimo de cobertura.
- [ ] CI sobe PostgreSQL + Redis para testes de integração.
- [ ] Migração Alembic `zero -> head` é testada.
- [ ] ARQ possui teste de integração.
- [ ] Busca PostgreSQL possui teste de integração.
- [ ] A documentação arquitetural reflete o código atual.

---


## Global Constraints

## Regra de implementação

Para cada alteração:

1. Criar ou ajustar teste primeiro quando possível.
2. Executar o teste e confirmar estado RED.
3. Implementar a menor mudança que resolva o comportamento.
4. Executar o teste novamente e confirmar GREEN.
5. Executar a suíte relacionada.
6. Rodar `ruff`, `mypy` e testes completos.
7. Commitar uma mudança coesa por vez.

---


## Restrições

- Não migrar para microserviços.
- Não introduzir Kafka, Kubernetes ou Elasticsearch.
- Não substituir PostgreSQL/Redis/ARQ sem evidência concreta de limitação.
- Não alterar comportamento funcional da ingestão sem teste de regressão.
- Não remover compatibilidade SQLite de desenvolvimento/testes sem decisão explícita.
- Não introduzir um novo modelo de IA antes de existir benchmark confiável.

## Task 1: Abstração explícita de fila de tarefas + remoção do fallback silencioso em produção

> Épico 1 (T1.1 + T1.2)

### T1.1 — Introduzir estratégia explícita de execução

Criar uma abstração pequena para execução de jobs.

Sugestão:

```text
app/interfaces/task_queue.py
app/services/task_dispatcher.py
```

Contrato mínimo:

```python
from typing import Protocol

class ITaskQueue(Protocol):
    async def dispatch_classification(self, article_id: int) -> str: ...
    async def dispatch_pdf(self, article_id: int, pdf_url: str | None) -> str: ...
```

Implementações:

```text
ArqTaskQueue
InlineTaskQueue
```

`InlineTaskQueue` deve ser usado apenas em desenvolvimento/testes.

---

### T1.2 — Remover fallback silencioso em produção

Regra:

```text
ENV=production
ENABLE_ARQ=true
Redis indisponível
→ erro explícito
```

```python
asyncio.create_task(...)
```

em produção.

## 01 ARQ_HARDENING

# Épico 1 — ARQ e Tarefas Assíncronas Persistentes

## Objetivo

Garantir que tarefas críticas não sejam silenciosamente degradadas para execução não persistente em produção.

---

## Problema atual

O dispatcher já utiliza ARQ, porém mantém fallback com:

```python
asyncio.create_task(...)
```

em:

```text
bhub-backend-python/app/services/task_dispatcher.py
```

Esse fallback é útil em desenvolvimento, mas não deve mascarar indisponibilidade de Redis/ARQ em produção.

Além disso:

```text
bhub-backend-python/app/jobs/tasks.py
```

ainda reutiliza lógica de:

```text
app/services/background_tasks.py
```

para processamento de PDF.

---

## Resultado desejado

### Produção

```text
API / serviço
    ↓
task_dispatcher
    ↓
Redis
    ↓
ARQ worker
    ↓
serviço de domínio
```

Se Redis/ARQ estiver indisponível:

```text
falha explícita
+ log estruturado
+ métrica/alerta
```

### Desenvolvimento/teste

Permitir executor local controlado, sem depender implicitamente de `asyncio.create_task()`.

---

## Tarefas

### T1.1 — Introduzir estratégia explícita de execução

Criar uma abstração pequena para execução de jobs.

Sugestão:

```text
app/interfaces/task_queue.py
app/services/task_dispatcher.py
```

Contrato mínimo:

```python
from typing import Protocol

class ITaskQueue(Protocol):
    async def dispatch_classification(self, article_id: int) -> str: ...
    async def dispatch_pdf(self, article_id: int, pdf_url: str | None) -> str: ...
```

Implementações:

```text
ArqTaskQueue
InlineTaskQueue
```

`InlineTaskQueue` deve ser usado apenas em desenvolvimento/testes.

---

### T1.2 — Remover fallback silencioso em produção

Regra:

```text
ENV=production
ENABLE_ARQ=true
Redis indisponível
→ erro explícito
```

Não executar automaticamente:

```python
asyncio.create_task(...)
```

em produção.

---

### T1.3 — Desacoplar job de PDF de background_tasks.py

Hoje:

```text
app/jobs/tasks.py
    ↓
app/services/background_tasks.py
```

Alvo:

```text
app/jobs/tasks.py
    ↓
app/services/pdf_service.py
```

ou criar uma operação transacional explícita:

```python
await pdf_service.process_article_pdf(article_id, pdf_url)
```

Essa operação deve concentrar:

- obtenção do artigo;
- download;
- validação;
- extração de metadados;
- persistência;
- atualização de status;
- commit/rollback controlado.

---

### T1.4 — Tornar jobs idempotentes

Executar o mesmo job duas vezes não deve duplicar:

- metadados PDF;
- associações;
- classificações;
- arquivos.

Adicionar testes para reexecução.

---

### T1.5 — Melhorar observabilidade

Registrar ao menos:

```text
job_type
job_id
article_id
attempt
status
duration
exception
```

Se OpenTelemetry já estiver ativo, registrar:

```text
arq.job.success
arq.job.failure
arq.job.duration
```

---

## Testes RED→GREEN

Criar:

```text
tests/integration/test_arq_jobs.py
tests/unit/test_task_dispatcher.py
```

Casos:

- [ ] Redis indisponível em produção não dispara `asyncio.create_task`.
